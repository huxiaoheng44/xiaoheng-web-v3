Drone Simulator

A flight task running on a TRENTOS-based companion computer that sends MAVLink commands to PX4 and flies a simulated drone in Gazebo to a predefined destination, guided by GPS and altitude sensor data.

Project overview

Goal: implement a flight task on the companion computer (TRENTOS) that sends actuator MAVLink messages to PX4 in order to fly the simulated drone to a predefined destination, guided by GPS and altitude sensor data from Gazebo.

System architecture

The system consists of four components:

  • Gazebo Garden – the simulator
  • PX4 – the flight control app (SITL)
  • C++ Proxy – bridges simulator sensor data to the companion computer
  • TRENTOS-based companion computer – runs the flight task

PX4 SITL (flight control app)

What is PX4?

“The brain of a drone”. Its architecture consists of concurrent modules that communicate asynchronously via the uORB message bus, and it talks to the outside world through MAVLink.

How to communicate?

Through PX4 startup and its predefined MAVLink channels.

What to communicate?

Flight modes – in particular offboard mode – and standard MAVLink messages.

Patches to PX4

PX4 almost has everything needed – except that the default PX4 drone model for Gazebo has no GPS or altitude sensor. Models are specified in SDF, an XML-based format, so the PX4-Autopilot repository was patched with:

  • a custom drone model
  • a custom world
  • a custom (minimal) MAVLink message channel

C++ Proxy & Gazebo

Two major questions: how to get sensor data from Gazebo, and how to communicate with TRENTOS.

Gazebo is a 3D robotics simulator with a plugin system for modifying models and pub-sub communication. The work needed was (1) sensor integration and (2) world modification.

Companion computer & MAVLink

MAVLink is a binary telemetry protocol and a transport-agnostic library. The most important commands used:

CommandPurpose in the flight task
MAV_CMD_DO_SET_MODESwitch PX4 into offboard mode
MAV_CMD_COMPONENT_ARM_DISARMArm the drone
SET_POSITION_TARGET_LOCAL_NEDSend position setpoints (take-off height, target coordinates)
MAV_CMD_NAV_LANDLand the drone

State machine

  1. PRE_READY initial state
  2. →
  3. CHANGE_MODE to offboard
  4. →
  5. ARM the drone
  6. →
  7. TAKEOFF to predefined height
  8. →
  9. FLY_PHASE to predefined coordinates
  10. →
  11. LAND

Network architecture

The TRENTOS application on the RPi 3 is connected to the host PC via Ethernet (point-to-point network 10.0.0.x/24). The host forwards UDP between 10.0.0.11 and host.docker.internal; inside Docker, the ds_px4 container runs Gazebo, PX4 SITL (sending to port 11001) and the C++ proxy (sending to port 11000).

Project details

Problems faced

  • Jansson: sys_clock_gettime() not implemented
  • Docker GUI (had to disable X11 authentication)
  • Firewall on NixOS
  • Socket can’t handle large traffic on QEMU
  • OS_Socket_recvfrom() bug (or feature?): when nothing is received, srcAddr is set to the last address from which something was received
  • Can’t use a more complex world (some models take a long time to load)

Ways to improve

  • UDP forwarding is a hassle – better utility scripts that set up all components (instead of opening many terminals); iptables in a production setting.
  • Make the flight task even more robust – handle the scenario where PX4 and Gazebo are killed and restarted.
