You Don’t Need RAG

粘贴一组 URL，得到一个干净的文本文件，或一个结构化、可直接用于 RAG 的 ZIP——按你的知识库实际需要来选。这个工具基于一个简单的判断：大多数“你需要 RAG”的问题，其实都装得进上下文窗口。

  • Next.js 15
  • React 19
  • Python 爬虫
  • 无向量数据库
  • 无嵌入
在线演示rag.huxiaoheng.com 源码github.com/huxiaoheng44/You-Don-t-Need-RAG

为什么做这个：RAG 已经成了万能答案

要查询文档？RAG。要回答关于某个网站的问题？RAG。要给聊天机器人提供上下文？RAG。这种模式确有价值——但也伴随着一长串实实在在的代价。

代价问题所在
分块会丢信息把文档切成固定大小的块，会破坏跨段落的上下文。模型只能看到碎片。
检索并不完美嵌入相似度不等于语义相关——模型照样会基于错误的分块自信作答。
运维负担重嵌入模型、向量数据库、数据摄取管道、检索层——每一环都可能悄无声息地出错或漂移。
评估困难没有一个显而易见的质量指标。幻觉可能来自技术栈的任何一层。
延迟累加每次查询都要先做一次嵌入请求和向量检索，LLM 才能看到第一个 token。
“工程师的本能是去找最复杂的工具。但复杂性本身就是负担，而不是解决方案。”

真正的解法：现代 LLM 已经能装下整个知识库

GPT-4o、Claude、Gemini 1.5 Pro 都支持 128K 到 1M+ token 的上下文窗口。一个 300 KB 的文本文件大约是 75K token。不分块，不检索，不搭管道。直接粘贴即可。

使用方式：四步完成，无需配置

01添加数据源

粘贴任何包含链接的内容——列表、邮件、Markdown 文档——所有 URL 都会被自动提取。也支持本地文件（PDF、TXT、MD、JSON、CSV）。

02审核

开始抓取前，URL 和上传的文件会分别列出——确认之前不会执行任何操作。

03抓取

抓取内容并测量其真实大小。

04导出

根据内容的实际大小，选择纯文本或 RAG ZIP。

输出：两种格式，按实际大小推荐

工具会测量实际抓取到的内容，并告诉你哪种格式合适——不需要你去猜。

并不反对 RAG：什么时候真的需要 RAG

这个工具不是反 RAG，而是讲求务实。以下情况下 RAG 才是正确选择：

  • 知识库确实很大——数百万 token，而不是几千。
  • 需要在实时更新的语料上实现亚秒级检索。
  • 需要在许多不同用户的私有数据集之间检索。
  • 查询非常具体，完整文档上下文大部分都会是噪声。

“其他所有情况——先试试纯文本文件。”
